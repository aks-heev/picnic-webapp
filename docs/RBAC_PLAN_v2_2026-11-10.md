- Customers are not a role. They keep `customer_select_own_bookings` only.

## 2. Design choice: add policies next to the old ones, don't edit them

Postgres ORs permissive policies together. So every new role gets **new** policies placed **beside**
the existing 82 email policies, which stay untouched until the last phase.

- No step before Phase 6 can lock the owner out: the old policy still matches his email.
- Every phase rolls back with `drop policy … ` on the new names (prefix `rbac_`). No restoring old SQL.
- Phase 6 then swaps the 82 email checks for `(select is_owner())` in one mechanical pass and drops nothing else.

Rejected alternatives: (a) rewriting all 82 policies up front (Aug plan, widest blast radius first);
(b) JWT custom claims (a fired user keeps access until token refresh, up to 1h); (c) a separate schema
or API for staff (doubles the surface).

## 3. Schema & helpers (Phase 1)

```sql
create table public.app_users (
  user_id      uuid primary key references auth.users(id) on delete cascade,
  role         text not null check (role in ('owner','manager','sales','viewer')),
  regions      text[] not null default '{}' check (regions <@ array['ncr','jaipur']),
  display_name text not null,
  is_active    boolean not null default true,
  created_at   timestamptz not null default now(),
  created_by   uuid references auth.users(id)
);  -- RLS on; owner-only R/W; a user may SELECT their own row
alter table public.expenses add column region text generated always as
  (case when lower(trim(city)) = 'jaipur' then 'jaipur' else 'ncr' end) stored;
```

Helpers: all `stable`, `security definer`, `set search_path = public, pg_temp`, EXECUTE revoked from `anon`:

| Function | Returns |
|---|---|
| `app_role()` | caller's active role or NULL |
| `is_owner()` | `app_role() = 'owner'` **OR `auth.email() = 'aksh.eeev@gmail.com'`** (fallback, removed in Phase 6) |
| `app_can_region(r text, cap text)` | owner → true; else active row whose role grants `cap` (`read`/`write`/`money`/`venue`) and `r = any(regions)` |
| `app_can_booking(id bigint, cap text)` | `app_can_region((select region from bookings where id = $1), cap)` |
| `my_access()` | `{role, regions, caps}` as json, for the frontends. The only thing the UI trusts |

🔴 Always call helpers wrapped as `(select app_can_region(region,'read'))` so Postgres evaluates them once per
statement (InitPlan), not per row.

## 5. Functions (Phase 3)

Each of the 15 gets its guard line replaced, **one function per migration**, by fetching
`pg_get_functiondef`, swapping only the guard expression and diffing old vs new before applying.
No full rewrite of any body (several are 8k+ chars).

| Function | New guard |
|---|---|
| `admin_add_manual_booking` | `app_can_region(<target venue's region>,'write')` |
| `admin_edit_booking`, `_postpone_`, `_reschedule_`, `_set_booking_food`, `_set_booking_split`, `_set_booking_checklist_extras`, `_apply_staff_extra_time`, `_resend_confirmation` | `app_can_booking(p_id,'write')`. 🔴 `admin_edit_booking` must also check the **new** venue's region when venue changes, so nobody can move a booking out of their region |
| `bookings_block_client_confirm` (trigger) | allow when `app_can_booking(NEW.id,'write')` |
| `admin_close_booking` | `app_can_booking(p_id,'money')` |
| `admin_set_package_prices` | `venue` cap on the venue's region |
| `admin_set_review_status` | `app_can_booking(…,'write')` |
| `admin_reorder_reels`, `admin_issue_staff_token` | `is_owner()` (unchanged in effect) |
| new `owner_set_user_role(email, role, regions[], active)` | `is_owner()`; writes `app_users` + audit |

`admin_resend_confirmation` is SECURITY DEFINER, so RLS does not protect it: its guard is the only check.

### Audit log (same phase, not optional)
`admin_audit_log(id, actor uuid, actor_role, action, booking_id, detail jsonb, created_at)`.
Insert-only from inside the functions. No UPDATE/DELETE policy for anyone. Owner reads.
Logged: confirm, discount (list total + agreed total + note), total edit, close, cancel/postpone,
role change, venue price change. A changed total with an empty note is rejected (existing
`admin_close_booking` rule extended to `admin_edit_booking`).

## 8. Verification: the access matrix

`supabase/tests/rbac_matrix.sql`: for each test user, inside `begin … rollback`:
```sql
set local role authenticated;
select set_config('request.jwt.claims', json_build_object('sub','<uid>','email','<email>','role','authenticated')::text, true);
-- then count/attempt per table and function, compare with the expected cell
```
The expected matrix is 7 identities (owner, manager-ncr, manager-jaipur, sales-ncr, viewer-jaipur,
phone customer, anon) × (class A-F tables + 15 functions). Must-pass cells:
1. sales → `booking_costs`, `expenses`, `unit_pnl_monthly` return **0 rows**
2. jaipur users → **0 NCR rows** in `bookings`, children, views
3. customer → only own bookings, nothing else new
4. manager-jaipur → `admin_edit_booking` moving a Jaipur booking to an NCR venue is **rejected**
5. anyone not owner → `owner_set_user_role`, `admin_issue_staff_token`, any DELETE are **denied**
6. `is_active=false` → next statement denied (no token-refresh wait)

Write tests run on one dedicated test booking (team phone, excluded from stats, own email) so no guest email fires.
Run the matrix after every phase. A phase isn't done until it's green.

## 10. Risks

|---|---|
